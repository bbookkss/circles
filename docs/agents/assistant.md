# Ask Circles

Ask Circles is a chat panel on every signed-in page. It tells a member what's
coming up and who's going. It lines up RSVPs for them to confirm, pulls up
their messages, finds circles by activity, and moves the Explore map to
another city.

- **Route:** `POST /api/assistant` (new), streaming
- **Model:** Claude Sonnet 5.5 (`claude-sonnet-5-5`)
- **Runs as:** the signed-in user's server Supabase client, so RLS applies to
  every tool
- **Mockup:** `mockups/assistant.js`, on any signed-in mockup page
  (git-excluded)

  U -.->|panel opens| SG[Suggested prompts<br/>no model call]

  subgraph RLS["User's Supabase client: RLS applies"]
    M --> W[my_week]
    M --> WG[whos_going]
    M --> P[propose_rsvp<br/>never writes]
    M --> MS[my_messages]
    M --> S[search_circles]
    M --> D[circle_details]
    W --> T1[(circle_members, circles,<br/>circle_schedules,<br/>circle_check_ins, profiles)]
    WG --> T2[(circle_check_ins, profiles)]

    S --> T4[(circles, circle_schedules)<br/>circle_member_counts]

  end

## Tools

| Tool | What it does | Reads / writes | Status |
| --- | --- | --- | --- |
| `my_week(days)` | Upcoming meets, the user's own answer and who's going | Reads `circle_members`, `circles`, `circle_schedules`, `circle_check_ins`, `profiles` | New |
| `whos_going(circle_id, occurs_on)` | Who said yes or maybe to one meet | Reads `circle_check_ins`, `profiles` | New |
| `propose_rsvp(items)` | Turns "say no to both" into one proposal per meet: `{circle_id, occurs_on, status}` | Writes nothing | New |
| `my_messages(from?, unread_only?)` | Recent or unread messages, optionally from one person, with "Open conversation" | Reads `messages`, `profiles`; filtered by `blocks` | New |
| `search_circles(query, place?)` | Circles by activity, near the user or in a named place | Reads `circles` (RLS), `circle_schedules`, `circle_member_counts` | New |
| `circle_details(circle_id)` | One circle's schedule and members. The exact place is included only for members. | Reads `circles`, `circle_places` | New |
| `go_to_place(name)` | Geocodes a place, then returns a client action that moves the Explore map | Forward geocoding (new); no database | New |

What the tools lean on that already exists:
- the `setCheckIn` and `clearCheckIn` server actions (`src/app/actions/checkins.ts`);
- `markConversationRead` (`src/app/actions/messages.ts`);
- the `circle_places` and `circle_member_counts` RPCs;
- `viewForPoints` and `distanceKm` (`src/lib/mapView.ts`).

## The agent proposes, the person decides

`propose_rsvp` never writes. Its proposals render as **one card per meet**,
each with its own **Confirm** and **Skip**:

- **Confirm** calls `setCheckIn` from the browser, as the user, the same as
  tapping Going on Home. The model isn't in that path.
- If the meet's check-in window isn't open yet, the `validate_check_in`
  trigger would refuse the answer. In that case Confirm writes a
  `scheduled_check_ins` row instead (new table, plus a cron to apply it when
  the window opens, alongside `src/app/api/cron/reminders`).
- Every card shows its state in words: **Not answered**, **Suggested, not
  sent**, **Sent**, or **Scheduled**, and offers **Undo** once sent or
  scheduled. There's no "confirm all": each meet is its own decision.

The same rule applies to messages. `my_messages` reads and links, and
replying happens in the conversation itself.

## Suggested prompts cost nothing

The panel's starter prompts aren't generated by the model. When the panel
opens, the route runs the same queries as `my_week` and unread messages, and
builds the prompts from them. For example:

- "Are you going to Thursday chess tomorrow?" (check-in open, unanswered)
- "Read Maya's message" (unread)
- "Who's going to the run?" (a meet this week)

No tokens are spent until the person asks something.

## Every circle comes with a map

Any circle in a reply renders with a thumbnail map: an exact dot for circles
the user is a member of (from `circle_places`), and an area for the rest.
The rule is the same as on Explore and the circle page. The thumbnail is
drawn from the tool result in the browser, not by the model.

## Guardrails

- RLS on every read. The assistant can't see a private circle, a blocked
  person's messages, or another circle's exact place, because the user can't.
- No writes from the model. RSVPs go through Confirm, and scheduled RSVPs
  through `scheduled_check_ins`, both as the user.
- Navigation and opening a conversation are client actions the user can see.
- It streams, and the logo ring in the panel spins while a tool runs.

## Open questions

- Whether conversations are stored. They aren't in the mockup.
- How far ahead `my_week` looks by default: 7 days or 14.
- Whether `my_messages` marks a conversation read when the assistant shows
  it. Probably not: only opening the thread should, through
  `markConversationRead`.
- Forward geocoding: Mapbox's forward endpoint is the obvious choice, since
  the token already exists.
